## What to build

The gateway verifies bearer tokens against an identity provider that publishes a standard OpenID Connect discovery document containing a `jwks_uri`, rather than requiring the provider to publish a signing key at its root URL. A deployment pointed at such a provider completes authorization normally with no code changes.

Signing-key acquisition moves behind a named resolver seam with two implementations: a standards-based one that follows `jwks_uri`, and the existing Keycloak root-URL `public_key` reader retained as an explicitly-named legacy adapter. A new optional setting selects the trust path, defaulting to a mode that tries the standard path first and falls back to the legacy one, so that the existing Keycloak deployment requires no configuration change.

Fetching the discovery document is unified with the existing startup fetch, so the gateway no longer makes two separate startup calls to the issuer. Startup-retry behaviour and the startup failure that names the relevant setting are preserved for both trust paths.

## Acceptance criteria

- [ ] Given an identity provider that publishes only a standard discovery document with a `jwks_uri` and a JWKS, a request carrying a correctly signed token is authorized normally.
- [ ] Given an identity provider that publishes only the Keycloak root-URL `public_key`, a request carrying a correctly signed token is authorized normally with the legacy adapter selected.
- [ ] Given the default trust-path setting, an identity provider publishing `jwks_uri` is used via the standard path, and one publishing only `public_key` falls back to the legacy adapter.
- [ ] Given an explicit trust-path setting, that path is used and no fallback to the other occurs.
- [ ] Given a token signed by the wrong key, the request returns 401 under every trust path.
- [ ] Given a trust path that is explicitly selected but unavailable on the provider, the gateway fails at startup with an error naming the setting that controls the choice.
- [ ] Given an unreachable identity provider, startup retries and then fails with an error naming the relevant setting and including the underlying cause.
- [ ] The issuer is fetched once at startup rather than twice.
- [ ] The Keycloak-specific issuer-metadata shape and the Keycloak-specific comments no longer appear in the main verification flow.
- [ ] The environment-variable documentation, the example environment file, and the identity-provider section of the README describe the new setting and state which existing settings remain Keycloak-specific.
